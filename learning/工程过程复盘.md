学习用 Git 与项目记录恢复开发过程，并区分项目历史、可能解释和推荐实践。

## 可观察的需求与约束

- 产品目标是把视频变成个人知识资产。
- 产品中文优先，默认使用 DeepSeek，视频处理优先使用字幕，ASR 可以关闭。
- 当前首先满足本地演示和作品集展示，完整生产 SaaS 尚未完成。
- 当前项目没有保存最初的用户访谈、容量指标、预算和服务等级目标。

## 从需求到实现的工程分解

### 需求分析

从“收藏视频未被消化”拆成获取、转写、理解、笔记、存储、检索和问答。这个分解在 README 和架构文档中明确出现。

### 系统设计

使用前后端分离、关系库加向量库、服务层加 provider 适配。这样使 UI、媒体处理、业务状态与语义检索保持不同边界。

### 技术选型

DeepSeek、ChromaDB、PostgreSQL、Next.js 和 FastAPI 均有实际代码；只有部分选择原因被文档记录。没有记录的动机只能作为可能解释，不能当作项目历史。

### 编码实现

代码采用模块分层：routes → services → models/providers。视频流程和 AI 流程进一步拆成独立服务或 Agent 节点。

### 测试

仓库只有一个自动化测试文件，验证 `/api/v1/health` 返回 200。

PROJECT_CONTEXT 记录前端（Frontend）typecheck/build 与后端（Backend）compile 曾通过；本轮未重新执行，因此这是此前记录，不是本次验证结果。

当前仓库看不出数据库、视频平台、LLM、ChromaDB 与端到端流程是否有独立自动化测试环境。

### 部署

本地 Compose 已实现；生产方案仍在三条路线中选择。开发 Dockerfile 的启动命令明确不适合生产。

## 真实过程与推荐流程对照

| 工程活动 | 仓库可确认状态 | 推荐下一步 |
|---|---|---|
| 产品目标与主流程 | 已确认 | 补充可量化成功指标 |
| 架构和 API 规划 | 已确认 | 用 ADR 记录后续重大选择 |
| 分阶段实现 | 文档声明，Git 粒度不足 | 每阶段小提交并附验收证据 |
| 自动化测试 | 仅健康检查可确认 | 增加 service、API integration 与端到端测试 |
| 数据库迁移 | 尚未生产化 | 引入 Alembic migration |
| 长任务执行 | MVP BackgroundTasks | 生产引入持久队列、重试和幂等 |
| 生产部署 | 未决定 | 先选择部署目标，再修改配置 |

## 不这样做会怎样

- 不分离关系库与向量库：业务一致性和语义检索职责混乱。
- 不验证 LLM JSON：模型格式变化会把错误数据写入数据库。
- 不保留 source：RAG 回答难以追溯，用户无法判断依据。
- 不做 migration：生产数据库 schema 演进不可审计、难回滚。
- 长视频继续依赖进程内 BackgroundTasks：进程重启可能丢任务，难以重试和横向扩展。
- 未选择部署平台就大改：可能同时引入不兼容的数据库、存储和网络方案。

## 历史缺口

- AI Coding Agent 的对话、逐步推理和被否决方案未保存在仓库中。
- 初始大提交之前是否实际按 Phase 1–6 顺序完成，现有 Git 历史无法判断。
- 当前仓库没有真实视频、DeepSeek 和 Chroma 的完整成功运行记录。
