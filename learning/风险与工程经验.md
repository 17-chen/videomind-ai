# VideoMind AI 错误、风险与工程经验

## 本章学习目标

学习区分当前问题、未来风险、可改进项和优秀实践。

## 当前可以直接看到的问题

本次静态分析没有发现可被失败测试直接证明的功能缺陷，因此这里不编造“曾经发生的错误”。

- 前端和后端 Dockerfile 使用开发启动命令。backend 的 `--reload` 和 frontend 的 `npm run dev` 适合本地开发；若原样用于生产，会造成性能、稳定性与镜像行为问题。
- 自动化测试只覆盖 API 健康检查。`backend/tests/test_videos.py` 只有一个测试，不能据此判断核心 Pipeline 是否正确。

## 技术债或工程风险

### 进程内长任务

- **证据**：`routes/videos.py` 使用 FastAPI `BackgroundTasks` 执行 `process_video_by_id`。
- **触发条件**：进程重启、任务超时、并发视频增多或需要重试。
- **影响**：任务可能丢失，无法可靠恢复，API 与工作负载争抢资源。
- **方向**：引入持久队列、独立 worker、重试和幂等状态机。

### 数据库 schema 无正式版本

- **证据**：`database/session.py` 使用 `create_all` 和硬编码 ALTER；requirements 虽有 Alembic，但无 migration 目录。
- **影响**：生产升级、回滚和环境一致性困难。
- **方向**：建立 Alembic baseline 与部署前 migration。

### demo user 不是认证

- **证据**：`get_current_user` 无条件调用 `get_or_create_demo_user`。
- **影响**：无法安全隔离真实多用户数据。
- **方向**：上线多用户前加入认证、授权和对象级访问控制。

### ASR 默认关闭

- **证据**：`ASR_PROVIDER=disabled`；字幕缺失时 transcriber 抛出业务错误。
- **影响**：无字幕视频无法完成处理。
- **方向**：明确 Demo 支持范围，或接入本地/托管 ASR。

### hash embedding 语义能力有限

- **证据**：`embeddings.py` 仅用字符/词 token 哈希到固定维度。
- **影响**：同义表达和复杂中文语义召回较弱。
- **方向**：建立检索评测集，再替换为中文 embedding 模型。

### 视频平台与本地存储

- **证据**：yt-dlp 直接访问平台，本地目录保存媒体与笔记，部署审计也记录平台限制。
- **影响**：云环境可能遇到网络、Cookie、版权策略、磁盘容量与持久化问题。
- **方向**：定义来源合规策略、对象存储和生命周期管理。

## 可改进项

- 将 processing 状态细分为 downloading、transcribing、analyzing、embedding，并记录阶段耗时。
- 为 AI 调用记录 provider、model、延迟和错误类别，但不记录密钥或敏感 prompt。
- 增加 service 单元测试、数据库 integration test、Chroma adapter test 与核心 E2E。
- 把 RAG system prompt 从代码移入版本化 prompt 资源，便于审查和实验。
- 将三个手动动作组合为可恢复的编排流程，同时保留单步调试入口。

以上均为**可改进项**，不代表当前 MVP 必然错误。

## 做得好的工程实践

- 配置集中在 Pydantic Settings，环境变量模板不包含真实 API key。
- 路由、服务、模型、provider 和 prompt 具有清晰边界。
- LLM JSON 经 Pydantic 验证后再持久化。
- RAG 返回来源视频，保留基本可追溯性。
- embedding 与 vector store 通过服务边界封装，为替换模型预留空间。
- 部署前先写审计与决策日志，避免未选平台就大规模重构。

## 无法确认的历史教训

- 无法确认项目曾因 LLM 格式、视频下载、数据库迁移或 Chroma 连接发生过真实故障。
- 无法确认被放弃的技术方案，除 `DECISION_LOG.md` 记录的“直接部署”外。
- 无法确认生产负载下的性能瓶颈。

## 本章小结与下一步

本项目最有价值的经验是：先用可替换组件跑通端到端闭环，再通过部署审计识别生产化缺口。下一步可以阅读《面试问题》，练习把这些判断表达成工程答案。
