# 用户密钥的离线事务式轮换

本工具只重新加密数据库 `ai_settings` 中的模型/ASR Key，不生成、安装或覆盖主密钥，不写 `.env`、私有密钥文件或平台配置，也不调用服务商。默认只读预检。应用仍仅使用一个 `USER_API_KEY_ENCRYPTION_KEY`，没有在线双密钥过渡能力。

## 使用前提

先在隔离恢复库演练，并按 [恢复手册](RECOVERY_RUNBOOK.md) 保存可恢复的数据库备份和独立安全保管的旧主密钥。准备由操作者安全提供的两个不同 Fernet 主密钥文件：只允许普通私有文件（0600 或更严格），最多128字节，UTF-8/ASCII兼容的Fernet文本及可选换行。拒绝最终符号链接、FIFO、目录、宽松权限和超大文件；父目录须由操作者保护。不要把密钥、连接串或真实用户数据写进命令行或文档。

数据库连接只从已有受保护环境 `DATABASE_URL` 读取。预检/执行要求可信后端角色可完整访问 `public.ai_settings`；有效 RLS 过滤、读取或权限错误均拒绝，不切换角色或关闭 RLS。执行只支持 PostgreSQL；事务内将搜索路径限定为pg_catalog/public，防止同名表遮蔽，结束自动恢复会话原设置。维护命令不能证明目标库选对、备份可恢复或进程已停止，必须先核对。

## 默认只读预检

```sh
python -m scripts.rotate_user_keys \
  --current-key-file /run/secrets/current-fernet.key \
  --next-key-file /run/secrets/next-fernet.key
```

按ID读取全部配置，验证旧主密钥能解开每个现有模型/ASR密文，并验证新主密钥加密后能解回相同字节；不调用任何模型，不更新数据库。PostgreSQL使用只读 repeatable-read 事务。默认最多10000行，可用 `--max-rows` 设置1–100000；超过预算整次失败，不分批轮换。没有密文时返回 `inconclusive`、退出2，不把空库当作轮换验证成功。

## 维护窗口与执行

1. 暂停新入队，等待队列没有 queued/running，确认无在途付费调用。停止所有 API、Worker、维护脚本和其他配置读写者，包括其他实例/主机。仅停止队列不足以停止同步设置编辑或问答。工具不自动停进程；`--writers-stopped` 是操作者确认，工具无法独立证明。不要以锁表代替维护窗口。
2. 在隔离演练和备份核验完成后，用同一目标库与两个受保护文件再次预检。
3. 显式执行：

   ```sh
   python -m scripts.rotate_user_keys \
     --current-key-file /run/secrets/current-fernet.key \
     --next-key-file /run/secrets/next-fernet.key \
     --apply --writers-stopped
   ```

4. 只有报告 `rotated` 才表示已收到事务提交成功。随后在所有仍停止的实例安全安装新主密钥，使用现有 `verify_key_recovery` 对新配置只读核验全部密文；确认后再恢复 API/Worker 并检查本人模型路径。工具不替操作者安装配置、重启或收费验收。旧主密钥必须继续与旧备份安全配对保存。

执行在一个事务内持有 `SHARE ROW EXCLUSIVE` 表锁，阻止并发INSERT/UPDATE/DELETE和其他轮换；它不阻止普通SELECT，不保护已经被进程缓存的密钥。锁等待最多5秒，单条SQL最多30秒。先验证全部源密文，再统一更新模型/ASR密文；flush后从数据库重新读取，要求行数/ID/两列密文与计划完全一致，并逐条用新主密钥解密，最后一次commit。NULL ASR保持NULL，用户/服务商/模型/创建时间不改，`updated_at` 随配置更新而刷新。原明文字节保持不变，但Fernet密文时间戳重新生成，不保留旧token时间。

坏旧密钥、损坏密文、RLS、超预算、权限或提交前SQL/触发器错误会失败，事务内全部写入回滚。不能只旋转“能解开的行”，也不能把部分用户留在旧密钥。检查不保证触发器的事务外副作用可撤回，不处理其他表或外部密钥系统。

## 结果和失败处理

输出仅为聚合JSON：状态、配置行数、密文数、是否已提交数据库写入，以及 `configuration_changed=false`。不输出密钥、明文/密文、ID、文件路径、连接信息或原始SQL异常。

- 退出0：`verified`（只读预检）或 `rotated`（已提交）。预检成功不是实际轮换，也不证明真实服务商可用。
- 退出1：`failed` 和固定原因。执行模式始终保守给出 `writes_may_have_occurred=true`；只读模式为false。
- 退出2：空库 `inconclusive`；参数错误也可能由argparse退出2。

**提交确认丢失时，失败响应不代表没写入。** 数据库保证事务整体提交或整体回滚，但客户端可能不知道是哪一种。此时保持全部API/Worker停止，分别用旧/新受保护文件运行只读 `verify_key_recovery --key-file`，确认当前全部密文由哪把密钥解开；核对后再选正确配置或恢复备份，不盲目重跑或直接改主密钥。本工具不会自动改回密文或安装任一配置。检查结果不一致或不可判定时保留停写状态调查。

需要回退时，优先按已演练的数据库备份与配对旧密钥恢复。若已确认全库均由新密钥加密且没有新写入，也可以在隔离演练后交换两个文件参数进行反向事务轮换；这仍是一次显式维护操作，不能只把环境变量改回旧值。

本轮只在合成数据库/密钥中验证；不代表真实用户主密钥、完整恢复、部署配置切换或本人模型计费已验收。
