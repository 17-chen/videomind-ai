# 本地数据与用户密钥恢复手册

更新：2026-10-27。本手册适用于当前 Docker Compose 本地部署；云端对象存储、pgvector 与目标平台尚未接入。恢复演练必须先在隔离环境完成，不能把正式数据卷作为试验目标。

## 要保留的内容

| 数据 | 当前位置 | 恢复检查 |
| --- | --- | --- |
| 用户、视频、转写、摘要、任务、加密后的用户 Key | PostgreSQL `postgres_data` | 备份可由 `pg_restore -l` 读取，隔离库迁移版本及行数可核对 |
| 下载/上传视频、音频、转写文本、Markdown 笔记 | `storage/videos`、`audio`、`transcripts`、`notes` | 文件按视频 ID 对账；文件仅在本地磁盘，数据库备份不会包含它们 |
| 本地 Chroma 向量 | `storage/chroma` | 与数据库同一时间点保留；不一致时按数据库重建索引 |
| Fernet 主密钥 | 环境中的 `USER_API_KEY_ENCRYPTION_KEY` | 独立安全备份，不与数据库转储同处；通过只读工具校验所有密文 |
| 视频平台 Cookie、服务商与部署凭证 | 未提交环境 | 各自独立备份；不要写入 Git、核查记录或命令输出 |

模型缓存可重新下载，不应将它视为唯一业务数据副本。数据库和文件目录分别备份会有时间差；一致性演练应先停止新入队并等待活动任务结束，再暂停 API/Worker 写入，记录同一恢复点。不要为了备份清空或重置现有数据卷。

## 备份与校验

1. 先用 `python -m scripts.task_queue_status` 确认 `queued=0`、`running=0`；若不为零，等待或安排维护窗口，不强杀可能正在调用付费服务的任务。
2. 暂停写入后，为数据库生成自定义格式转储。先在宿主执行 `umask 077`，备份目标放在 Git 忽略的 `storage/backups/`；例如 `docker compose exec -T postgres pg_dump -U videomind -Fc videomind > storage/backups/videomind-YYYYMMDD.dump`。实际数据库名和用户应从当前部署配置确认，不照搬示例。检查文件非空，再用 `docker compose exec -T postgres pg_restore -l` 读取转储清单；可将备份以只读输入重定向给该命令。
3. 另行备份上述业务文件目录和 Chroma 目录，并记录备份时间、文件数与校验摘要。不要将 `.env`、Cookie 或主密钥混入可共享归档。备份文件只授予操作者读取权限，并按部署的保留与异地存储策略保存。
4. 对当前配置运行 `docker compose exec -T backend python -m scripts.verify_key_recovery`。若要验证从安全备份取回的主密钥，在**隔离环境**把私有文件以只读方式挂载到容器，然后运行 `python -m scripts.verify_key_recovery --key-file /run/secrets/fernet.key`。文件必须是普通文件、权限 `0600`；工具只输出总行数与密文数，不输出 ID、密文或明文。`verified` 且退出码 0 表示所有现存密文可解；`inconclusive` 且退出码 2 表示没有密文，不能证明密钥正确；`failed` 且退出码 1 表示配置、读取或解密有问题。

`pg_restore -l` 只验证归档结构，不代表数据可成功恢复。Fernet 校验也只覆盖数据库中的用户 Key，不验证服务商账号可用、视频文件或向量索引。

## 隔离恢复演练

1. 使用单独的数据库名、存储目录和环境配置，禁止指向正在使用的 `postgres_data` 或 `storage/`。先在隔离库执行转储恢复，再核对 Alembic 版本、用户/视频/任务行数及关联完整性；版本不匹配时先查明原因，不盲目 `stamp head`。
2. 恢复同一时间点的业务文件与 Chroma 副本。逐项抽查数据库记录引用的本地文件存在；向量缺失或不一致时，在隔离环境先用 `python -m scripts.reindex_vectors --dry-run` 对账，再决定是否重建。
3. 在隔离环境装入备份主密钥并执行只读校验；只有 `verified` 才能判定现存用户 Key 具备解密证据。真实 Supabase 登录、服务商调用与最终问答需要独立验收，不能用合成密钥测试替代。
4. 记录演练时间、恢复点、数量、失败项和修复动作。正式切换前仍需确认新写入已停止、回滚入口与用户影响。

## 主密钥轮换边界

当前业务代码仅使用一个 Fernet 主密钥，**尚无在线轮换能力**。不能直接覆盖 `USER_API_KEY_ENCRYPTION_KEY`；否则已有密文无法解开。轮换实现前，先保存旧密钥和数据库可恢复备份，在隔离库验证旧密钥可解开全部密文，再设计事务内重新加密、逐条新密钥验证和失败回滚，最后安排 API 与 Worker 协同切换。若检查出现 `inconclusive`，说明没有可验证样本，应保留这一限制，不能标记轮换验收通过。

## 删除与排错

删除本人视频的顺序是：按用户删除 Chroma 向量、提交数据库删除、清理同 ID 的本地文件。Chroma 删除失败时数据库行保留，可重试；数据库提交失败时向量可能已经移除，记录仍在，可重新入库；文件清理失败时日志记录视频 ID 和错误类型，数据库行已消失，需要人工核对残留文件。三处没有共同事务，不应声称删除具备原子性。

排错时先查 `X-Request-ID`、任务 ID、队列快照、API/Worker 日志和 readiness，再查磁盘与数据库；不要把原始视频 URL、Cookie、用户 API Key 或异常正文复制到共享日志。恢复前确认目标环境和备份来源，避免把隔离演练误做在正式数据上。

## 2026-10-29：文件总量与阶段临时目录

正式文件按视频归属计入用户配额；`.staging-*` 是阶段临时目录，SIGKILL 可能留下它们。不要按名称或时间直接批量删除：先核对队列、存活 Worker 和文件归属，确认没有在途生成，再在备份/隔离环境演练清理。删除记录后清理失败的孤立文件不再出现在用户配额中，需要单独与实际磁盘占用对账。此轮没有自动清理这些目录或业务文件。配额与跨存储失败边界见 [说明](STORAGE_QUOTA.md)。
