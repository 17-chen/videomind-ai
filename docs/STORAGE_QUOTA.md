# 每用户本地文件总量

2026-10-29：R8 本地业务文件配额子项。保留现有上传视频配额，不需要数据库迁移。

## 配置与用户反馈

- `MAX_UPLOAD_MB=1024`：单次上传大小。
- `MAX_USER_UPLOAD_MB=5120`：本人上传来源视频累计容量，沿用既有规则。
- `MAX_USER_STORAGE_MB=10240`：本人正式保存的业务文件累计容量，包括上传视频、URL 下载视频及字幕、提取音频、转写文本、AI/手工 Markdown 笔记。所有 MB 均按 1024 × 1024 字节计算。
- 上传与手工笔记保存超限返回 HTTP 413，并提示先删除不需要的视频；上传策略接口公开总量上限，页面以中英文显示。
- 异步任务的 HTTP 202 仍表示入队。Worker 在生成文件发布时超限，将视频与任务标为失败，保留明确的容量错误；不把入队响应改为同步 413。

## 核算和并发

以数据库中属于当前用户的视频 ID 为归属，在配置的 video/audio/transcript/note 四类目录中统计同 ID 前缀的正式文件。成功与失败任务已保存的文件都计入；同一个文件路径只计一次。旧文件无需建立字节台账或迁移数据，其他用户文件不占本人的额度。

下载、音频提取和文本生成先写入对应根目录下私有的 `.staging-*` 临时目录。阶段完成后锁定 PostgreSQL 用户行，重新统计已保存文件，扣除同名旧文件大小，再加上本次输出的实际大小。通过后锁定并核对视频归属，逐文件使用 `os.replace` 发布，然后提交并释放数据库锁。上传也使用同一用户行锁，因此上传和 Worker 文件发布共用额度；网络/模型调用和音频提取期间不持有这把锁。

字幕同下载视频作为一组核算；字幕解析得到的 TXT 转写单独核算。配额拒绝发生在任何替换之前，因此不会覆盖本阶段的旧文件。后续音频/转写/笔记阶段失败时，先前已经通过核算的视频等文件继续保留、计费，供用户查看、重试或删除。

同名文件替换按净增长判断，等大替换或缩小仍可进行，包括已有文件超过新配置上限的情况。生成期间视频已经被删除时拒绝发布，避免新建无归属文件。当前删除成功清理文件后释放占用，沿用现有向量 → 数据库 → 文件的顺序。

并发证据仅覆盖真实 PostgreSQL 双会话与同一文件系统；云端对象存储、多实例独立磁盘不满足此实现前提。

## 存储和故障边界

- 这是**有数据库视频归属的正式业务文件**配额。数据库正文/JSON、Chroma 索引、模型缓存、备份、临时上传正文、上传提交前无视频记录的 `.part`、`.staging-*` 及没有视频记录的孤立文件不在此额度中。真实磁盘总占用可能更大。
- 2026-10-31 已补[阶段检查点保护与音频单文件上限](TEMPORARY_STORAGE.md)，但没有统一空间预留或下载合并全程硬上限；大媒体生成过程中仍可能占用超出剩余额度的临时空间。生成成功但发布超限时删除临时目录；SIGKILL 可能留下临时目录。不能将此实现当作磁盘耗尽防护全部完成。
- 配额按实际生成结果判定；已完成的 ASR/AI 调用可能已经计费，即使文件最终未能保存。发生这类错误后应先释放容量，再按用户意愿手动重试，不能承诺无重复计费。
- 文件系统和数据库不是一个原子事务。发布中途 I/O 失败或 SQL 提交失败时，部分已发布文件可能保留；只要视频记录还在，下次核算仍会统计它们。数据库笔记可能与磁盘文件暂时不同，沿用恢复手册中的重新保存/检查规则。
- 删除已提交但文件清理失败时，孤立文件暂时不再计入该用户的配额。2026-10-30 已有[只读聚合对账](STORAGE_MONITORING.md)；仍需主机告警与可恢复清理，不能仅依赖用户配额估算实际磁盘使用量。
- 目录扫描适合当前本地规模；大规模资料库需要持久化文件账本、可恢复清理和对象存储适配。手工移动文件或修改存储根目录应先停写并核对映射。

恢复与清理见 [恢复手册](RECOVERY_RUNBOOK.md)，本轮检查见 [核查记录](VERIFICATION_2026-10-29.md)。
